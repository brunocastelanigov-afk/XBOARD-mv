## Status

## Story

**As a** gestor de tráfego,
**I want** uma página no dashboard que mostre, por campanha, a receita combinada de vendas front + upsell, filtrável por funil/país/variante/período (igual às demais páginas do dashboard) e ordenada pelas campanhas de maior ROI,
**so that** eu consiga decidir em quais campanhas investir mais sem precisar pedir para uma IA cruzar manualmente UTM e e-mail de cada venda.

## Acceptance Criteria

1. Uma nova rota `/roi-campanhas` é adicionada ao roteador (`main.tsx`) e um item correspondente ("ROI de Campanhas") aparece na sidebar (`app-sidebar.tsx`), seguindo o mesmo padrão visual dos itens existentes (Respostas, Resultados, Performance Geral, Auditoria de Leads).
2. A página exibe o **mesmo `FilterBar` já usado nas outras páginas** (funil, país, variante e período), reaproveitando `useDashboardFilters()`/`DashboardFiltersContext` — **não** um filtro de período isolado. *(Isso muda em relação à v0.1 desta story: como a Story 1.1 agora grava a compra Lastlink como evento associado a um `lead_id`/`funnel_id`/`country`/`funnel_variant`, o escopo de filtro passa a ser o mesmo do resto do dashboard.)*
3. Ao carregar ou alterar qualquer filtro, a página busca dados via `fetchCampaignRoi(filters)`, que chama a RPC `rpc_campaign_roi` (Story 1.1) com os mesmos parâmetros de escopo (`p_funnel_id`, `p_country`, `p_funnel_variant`, `p_date_from`, `p_date_to`) usados pelas demais RPCs.
4. Os resultados são exibidos em uma tabela (`DataGrid`) com uma linha por campanha (`utm_source` + `utm_campaign`), **ordenada por receita total decrescente** — ou seja, a campanha com maior ROI aparece primeiro. *(Ver nota de ambiguidade em Dev Notes sobre "ordem crescente" no pedido original.)*
5. Cada linha da tabela mostra, no mínimo: nome da campanha, mídia (`utm_medium`), número de vendas front, número de vendas upsell, receita front, receita upsell e receita total — valores monetários formatados em BRL.
6. Um bloco de métricas no topo da página (`MetricCard`) resume, para os filtros aplicados: receita total combinada (líquida, já descontando estornos), receita front, receita upsell, receita não atribuída (`unmatched_revenue_cents` — vendas cujo `lead_id`/`Vtid` não bateu com nenhum evento de funil conhecido, ver Story 1.1 AC 5) e total estornado (`reversed_revenue_cents` — soma de refunds/chargebacks, ver Story 1.1 AC 7).
7. Estados de carregamento usam `Skeleton` (mesmo padrão de `performance.tsx`); erro de busca mostra mensagem inline consistente com as demais páginas; ausência de dados usa o estado vazio nativo do `DataGrid` ("Nenhum dado encontrado.").
8. A página segue os tokens visuais e componentes já existentes (`atoms/`, `composites/`) — nenhuma nova biblioteca de UI ou padrão visual é introduzido.
9. `npm run lint` e `npm run build` (`tsc -b && vite build`) rodam sem novos erros após a mudança.
10. Validação manual: com dados reais ou de teste, confirmar que alterar qualquer filtro (funil, país, variante ou período) altera o conjunto de resultados e que a ordenação por receita total está correta.

### Contrato de Dados (alinhado com a RPC da Story 1.1)

```typescript
// dashboard/src/lib/dashboard-types.ts
export interface CampaignRoiRow {
  utm_source: NullableString
  utm_campaign: NullableString
  utm_medium: NullableString
  front_revenue_cents: number
  upsell_revenue_cents: number
  total_revenue_cents: number
  front_orders: number
  upsell_orders: number
  unmatched_revenue_cents: number // vendas sem lead_id/Vtid resolvido (Story 1.1 AC 5)
  reversed_revenue_cents: number // total estornado (refund + chargeback), já descontado de front/upsell/total (Story 1.1 AC 7)
}
```

```typescript
// dashboard/src/lib/dashboard-queries.ts
export async function fetchCampaignRoi(filters: DashboardFilters, signal?: AbortSignal) {
  return readRows<CampaignRoiRow>(
    supabase.rpc("rpc_campaign_roi", scopeParams(filters)),
    signal
  )
}
```

Nota: o campo `attributed_upsell_orders` que existia na v0.1 desta story foi removido do contrato — pertencia ao mecanismo antigo de "crosswalk venda→venda por e-mail", que não existe mais na Story 1.1 (v0.4 usa `lead_id` passado via `Vtid` no link de checkout, determinístico). `unmatched_revenue_cents` mostra receita que existe mas não pôde ser ligada a nenhuma sessão de funil conhecida.

### Filtro — agora reaproveita `FilterBar`/`useDashboardFilters` por inteiro

Correção em relação à v0.1 desta story: como a Story 1.1 passou a gravar a compra Lastlink como um evento na mesma tabela `funnel_events` (real, confirmada por mapeamento direto do Supabase), associado a `lead_id`/`funnel_id`/`country`/`funnel_variant`, vendas Lastlink **deixaram de ser um domínio de dados à parte** — elas vivem no mesmo funil/lead que o resto do dashboard. Por isso esta página usa `useDashboardFilters()` e `<FilterBar showSearch={false} />` exatamente como `performance.tsx`/`auditoria.tsx`, sem estado de filtro local. O `DashboardFiltersContext` (`dashboard/src/contexts/dashboard-filters-context.tsx`) já populado a partir de `rpc_dashboard_filter_options` cobre `funnelId`/`country`/`funnel_variant`/período igualmente bem para esta página.

### Nota de ambiguidade no pedido original (assunção documentada)

O pedido original menciona "uma tabela em ordem crescente... contendo as campanhas com o maior número de ROI". Esses dois trechos são tecnicamente contraditórios (ordem crescente = valores do menor para o maior; "maior ROI" sugere querer ver os melhores primeiro). **Assunção adotada nesta story**: a tabela é ordenada por receita total **decrescente** (ranking: melhor campanha no topo), que é o padrão usual para uma tabela de "top campanhas" e é o que a RPC da Story 1.1 já retorna. Se o usuário quis dizer literalmente ordem ascendente por valor, é um ajuste trivial de `order by` na RPC ou de sort no client — sinalizar para @po/usuário confirmar durante a revisão do draft.
