# Story 15.2: Split de ambiente staging/produção no dashboard

Status: Review

## Objetivo

Introduzir, no `melhor-versao-dashboard`, um **segundo client de Supabase
Auth dedicado ao CRM** — distinto do client de Tráfego existente em
`src/lib/supabase.ts` — apontando por ambiente para o Supabase do app
(staging `lcylofpnwlwaicewhsfl`, produção `shyzagfnifqitpmyurol`),
conforme Decisões 1 e 4 da Story 15.1. Adicionar também a variável de URL
do worker por ambiente, usada pelas futuras chamadas `/admin/*` das
Stories 15.5+. Nenhuma role gate, nenhuma integração de página CRM — só a
infraestrutura de ambiente/clients que desbloqueia as Stories 15.3 a 15.9.

## Contexto

A Story 15.1 fechou (Status: Done) as decisões arquiteturais que esta
story implementa:

- **Decisão 1:** a conta CRM autentica **diretamente no Supabase do app**
  por ambiente, com `role: "admin"` já presente no token — sem troca ou
  emparelhamento de token com o worker. Consequência arquitetural
  registrada explicitamente na Story 15.1: "o dashboard precisa suportar
  **dois clients de Supabase Auth distintos** — um apontando para
  `zcaypxqrteoedzbdmagm` (login de Tráfego, inalterado) e outro apontando
  para o Supabase do app por ambiente (login de CRM) [...] isso deve ser
  tratado como parte do escopo técnico da Story 15.2".
- **Decisão 4:** login do time de Tráfego (`isAllowedTeamUser`) permanece
  isolado no Supabase de campanhas (`zcaypxqrteoedzbdmagm`), inalterado.
  Login e dado de CRM usam o Supabase do app, por ambiente. **Não
  compartilham** — não existe ponte/troca de token entre os dois.

Hoje `src/lib/supabase.ts` exporta um único client (`supabase`), lido de
`VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY`, apontando para
`zcaypxqrteoedzbdmagm` — usado por `auth-context.tsx` (login/sessão),
`app-sidebar.tsx`, `dashboard-queries.ts`, `login.tsx`,
`forgot-password.tsx` e `reset-password.tsx`. Não existe hoje nenhum
`.env.staging`/`.env.production` no dashboard — só um `.env` único (não
versionado, valores reais) e um `.env.example` (versionado, vazio) com as
mesmas duas variáveis. Não existe nenhuma variável `VITE_API_*` no
dashboard — nenhuma página faz `fetch` ao worker hoje.

Convenção Vite já usada nos outros dois frontends do monorepo
(`treino-trinca-app/frontend`, `treino-trinca-app/app-treino`, ambos lidos
como referência): `.env` carrega os valores de desenvolvimento local
(hoje apontando pro Supabase de staging do app, por conveniência de dev),
`.env.production` (gitignored, nunca committado) sobrescreve para o build
de produção via `vite build` (modo `production` por padrão). Em ambos os
casos, o Vercel/hosting de produção injeta as env vars reais via
dashboard do provedor — os arquivos `.env*` locais nunca são a fonte de
verdade do ambiente deployado, só um fallback de build/dev. O dashboard
(`melhor-versao-dashboard`) roda hoje na Vercel, projeto `xboard-mv`
(confirmado em `.env.local`, token OIDC da Vercel), mesmo padrão de
branch `develop` = staging usado por `frontend`.

`docs/staging.md` e `docs/production.md` (lidos em
`treino-trinca-app`, únicas fontes existentes desse par staging/produção
no monorepo) confirmam as URLs do worker por ambiente:

- Staging: `https://api3.desafiotreinotrinca.online`
- Produção: `https://api.desafiotreinotrinca.online`

## Dev Notes

- **Não renomear as variáveis existentes.** `VITE_SUPABASE_URL`/
  `VITE_SUPABASE_ANON_KEY` continuam significando "client de Tráfego" —
  renomear para algo como `VITE_SUPABASE_TRAFFIC_URL` pareceria mais
  simétrico com `VITE_SUPABASE_CRM_URL`, mas exigiria atualizar a
  variável já configurada no dashboard da Vercel em produção sem
  necessidade, criando risco de deploy quebrado por variável ausente.
  Prefira o nome novo assimétrico (`_CRM_`) e deixe o existente como
  está — é a opção de menor raio de explosão.
- `dashboard_role` (Decisão 2 da Story 15.1, valor `"crm"`) passa a viver
  em `app_metadata` da conta **no Supabase do app**, lida via
  `supabaseCrm.auth.getSession()` — mas isso só acontece quando
  `auth-context.tsx` for estendido para suportar dois clients (fora do
  escopo desta story, ver "Fora de Escopo").
- `VITE_API_URL` nesta story é só a variável — nenhum client HTTP
  (`fetch` wrapper, `Idempotency-Key`, etc.) é criado. Isso é escopo das
  Stories 15.5+, que vão consumir `/admin/*` de fato.
- `.env.local` (Vercel CLI, `VERCEL_OIDC_TOKEN`) não é tocado nesta
  story — é gerado automaticamente pelo `vercel` CLI e já está no
  `.gitignore` (`.env*`).
