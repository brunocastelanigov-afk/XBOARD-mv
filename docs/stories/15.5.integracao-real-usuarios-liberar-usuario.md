# Story 15.5: Integracao real — Usuarios e Liberar Usuario

Status: Review

## Objetivo

Substituir os dados fabricados de `src/pages/usuarios.tsx` e
`src/pages/liberar-usuario.tsx` por leitura/escrita real dos contratos
admin ja entregues pelo Epic 14, usando a sessao CRM do Supabase do app e
`VITE_API_URL` da Story 15.2.

## Contexto

Story 15.1 decidiu que contas CRM autenticam diretamente no Supabase do
app por ambiente, com `dashboard_role = "crm"` e `role = "admin"` no token.
Story 15.2 criou `src/lib/supabase-crm.ts` e `VITE_API_URL`. Stories 15.3
e 15.4 fecharam o role gate de sidebar e rota protegida.

No estado atual, `usuarios.tsx` ainda usa `MOCK_LEADS`,
`MOCK_REAVALIACAO_DIAS`, `MOCK_LAST_APPLIED_TEXT`, `setTimeout` para
loading/sucesso e `buildUserDetail()` local. `liberar-usuario.tsx` ainda
usa `MOCK_ALUNOS`, `buildMockProtocoloDetalhe()`, `EXERCICIO_SEARCH_GROUPS`,
`nextMockId()` e `setTimeout` para criar, buscar e salvar. Nenhuma das duas
paginas chama o worker.

O worker ja possui as mutacoes necessarias em `/admin/*`:
`POST /admin/users`, `PATCH /admin/users/:userId/access`,
`POST /admin/users/:userId/release`, `POST /admin/users/:userId/password-temp`,
`PATCH /admin/settings/reassessment` e `GET/PATCH /admin/users/:userId/program`.
As leituras devem usar somente os contratos read-only `admin_*` existentes.

## Escopo

1. Criar um client/helper admin no dashboard para chamadas reais:
   - base URL de `import.meta.env.VITE_API_URL`;
   - token de `supabaseCrm.auth.getSession()`;
   - header `Authorization: Bearer <access_token>`;
   - parse padronizado de erro real do worker;
   - geracao de `Idempotency-Key` para toda escrita admin.
2. Integrar `usuarios.tsx`:
   - lista/busca/filtros confirmados via `admin_users_list`;
   - detalhe via `admin_user_detail`;
   - ranking por faturamento via `admin_users_revenue_rank`;
   - busca por e-mail quando necessario via `admin_user_lookup_by_email`;
   - prazo global de reavaliacao via contrato real de settings e
     `PATCH /admin/settings/reassessment` com `Idempotency-Key`.
3. Integrar `liberar-usuario.tsx`:
   - criar usuario via `POST /admin/users`;
   - liberar usuario via `POST /admin/users/:userId/release`;
   - emitir senha temporaria via `POST /admin/users/:userId/password-temp`;
   - buscar usuario existente por e-mail via `admin_user_lookup_by_email`;
   - se mantida a edicao de protocolo individual da pagina, carregar via
     `GET /admin/users/:userId/program` e persistir via
     `PATCH /admin/users/:userId/program`, sempre com `Idempotency-Key`.
4. Remover `MOCK_*`, arrays fabricados equivalentes e IDs fabricados
   (`mock-*`, `nextMockId`, `Date.now()` para entidade) dessas duas paginas.
5. Implementar estados reais de loading, vazio, erro, sucesso e replay sem
   fallback fake.

## Decisoes Bloqueantes

1. **Filtros/labels sem confirmacao visual ou contrato claro em Usuarios.**
   O arquivo atual sinaliza que as opcoes de "renda" foram reaproveitadas
   por analogia e que "frequencia" so tem alta/baixa confirmado. Antes do
   Develop, decidir uma das opcoes:
   - remover temporariamente esses filtros e manter apenas filtros com
     contrato claro;
   - manter os labels atuais por decisao explicita do usuario;
   - derivar labels das respostas reais do quiz, apos mapear o payload real.

   Resolucao: usuario aprovou explicitamente a remocao/substituicao dos
   blocos mockados. A implementacao removeu filtros de renda/frequencia sem
   contrato claro e manteve filtros derivados de campos reais da lista:
   objetivo, sexo e status.

## Dev Notes

- `POST /admin/users` aceita `{ email, nomeCompleto, tier }`, com `tier`
  real do backend em `"mvp" | "elite"`. A UI hoje chama o plano Trinca;
  mapear Trinca para `mvp` no payload e para `PlanBadge plan="trinca"` na UI.
- `POST /admin/users/:userId/release` aceita `{ tier }`.
- `POST /admin/users/:userId/password-temp` retorna `{ status,
  temporaryPassword }` somente na chamada original; replay retorna
  `{ status: "already_issued" }`.
- `PATCH /admin/settings/reassessment` aceita `{ reassessmentDays }`, inteiro
  `1..365`.
- `PATCH /admin/users/:userId/access` existe, mas o escopo minimo pedido
  para `liberar-usuario.tsx` cita criacao, liberacao e senha temporaria.
  Usar `access` somente se a UI atual precisar persistir alteracao de
  status/plano fora do fluxo de liberacao.
- Para leitura `admin_*`, seguir o Read/Write Boundary do Epic 14: o
  dashboard nunca usa service role nem tabela base.
- A pagina `liberar-usuario.tsx` mistura liberar usuario com edicao de
  protocolo individual. Se essa edicao permanecer visivel nesta story, ela
  nao pode continuar mockada; usar `GET/PATCH /admin/users/:userId/program`
  ou esconder/desabilitar a parte fora do escopo somente apos aprovacao,
  porque remover conteudo exige confirmacao.
