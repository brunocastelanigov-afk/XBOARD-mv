# Story 15.6: Integracao real — Protocolos, Regras e Banners

Status: Review

## Objetivo

Substituir os dados fabricados de `src/pages/protocolos.tsx`,
`src/pages/regras.tsx` e `src/pages/banners.tsx` por leitura e escrita
reais usando os contratos `/admin/*` já existentes no worker do
`treino-trinca-app`, com token CRM emitido pelo Supabase do app e
`VITE_API_URL` configurado pela Story 15.2.

## Contexto

As Stories 15.1 e 15.2 estao `Done` e fecham as dependencias desta
story:

- A conta CRM autentica diretamente no Supabase do app por ambiente, com
  `role: "admin"` no JWT. O token da sessao CRM deve passar em
  `verifyAuth` e `adminGuard` do worker sem endpoint de troca.
- `dashboard_role` para o grupo CRM e exatamente `crm`.
- `src/lib/supabase-crm.ts` existe e expoe `supabaseCrm`.
- `VITE_API_URL` existe por ambiente e aponta para o worker:
  staging `https://api3.desafiotreinotrinca.online`, producao
  `https://api.desafiotreinotrinca.online`.

O Epic 15 define esta story como a integracao real de Protocolos,
Regras e Banners. O worker ja contem os contratos do Epic 14 em
`worker/src/routes/admin/protocol-templates.ts`, `programs.ts`,
`classification-rules.ts` e `banners.ts`; esta story deve apenas
consumi-los no dashboard. Nao criar rota, contrato `admin_*` novo,
migration ou backend paralelo.

## Escopo

1. `protocolos.tsx`
   - Ler `admin_protocol_templates_tree`.
   - Ler `admin_user_programs_list`.
   - Ler detalhe de treino individual via `admin_user_program_detail`.
   - Criar/editar/excluir templates via `/admin/protocol-templates*`.
   - Editar treino individual via `PATCH /admin/users/:userId/program`.
   - Remover `MOCK_CATEGORIAS`, `MOCK_ALUNOS`, IDs fabricados e timers de
     loading fake.
2. `regras.tsx`
   - Ler `admin_classification_rules_list`.
   - Ler `admin_quiz_fields`.
   - Criar/editar/excluir regras via `/admin/classification-rules*`.
   - Testar regras via `POST /admin/classification-rules/test`; o
     frontend nao replica a logica de classificacao.
   - Remover `MOCK_RULES` e IDs fabricados.
3. `banners.tsx`
   - Ler `admin_banners_list`.
   - Criar/editar/excluir banners via `/admin/banners*`.
   - Enviar conflitos de `plano + ordem` ao backend e exibir o erro real
     `409`, sem bloqueio client-side divergente.
   - Remover `MOCK_BANNERS` e IDs fabricados.
4. Adicionar estados reais de loading, erro, salvamento e exclusao nas
   tres paginas, preservando os estados forcados por query string
   (`loading=1`, `empty=1`, `canEdit=false`) usados pelo catalogo/testes.

## Criterios de Aceite

- Nenhum `MOCK_*` remanesce em `protocolos.tsx`, `regras.tsx` ou
  `banners.tsx`.
- Nenhum ID novo e fabricado com `mock-${Date.now()}` ou equivalente
  remanesce nas tres paginas.
- CRUD/listas das tres paginas usam `/admin/*` real via `VITE_API_URL` e
  token CRM de `supabaseCrm`.
- O testador de regras chama de fato
  `POST /admin/classification-rules/test`.
- O frontend nao replica a logica de classificacao do backend.
- Banners nao fazem validacao client-side divergente de duplicidade
  `plano + ordem`; conflito real `409` do backend e exibido ao usuario.
- Loading e erro das tres paginas refletem chamadas reais, com fallback
  visual claro.
- Nenhuma rota/contrato `admin_*` novo, migration ou backend paralelo foi
  criado.

## Testes

  - Regras carrega lista/campos reais, salva/exclui via
    `/admin/classification-rules*` e o testador chama
    `/admin/classification-rules/test`.
  - Protocolos carrega arvore/lista/detalhe reais e envia mutacoes para

## Dev Notes

- Usar `supabaseCrm.auth.getSession()` para obter o token da conta CRM.
  Se nao houver token, a UI deve expor erro real de autenticacao em vez
  de cair para dado mock.
- Todas as mutacoes admin do worker usam `Idempotency-Key`; gerar chave
  por submissao no frontend para POST/PATCH/DELETE.
- Payloads devem seguir os nomes do worker:
  - Protocolos: `nome`, `categoria`, `etiqueta`, `descricao`, `nivel`,
    `objetivo`, `duracaoMinutos`, `dias`, `exerciseId`,
    `repsOuDuracao`, `descansoSegundos`.
  - Regras: `nome`, `descricao`, `prioridade`, `condicoes`,
    `nivelResultado`, `override`, `ativo`; teste envia
    `{ respostas: [{ pergunta, resposta }] }`.
  - Banners: `plano`, `ordem`, `imagemUrl`, `link`, `ativo`.
- Mapear exibicao em portugues apenas na borda da UI; os valores enviados
  ao backend devem permanecer no contrato real (`iniciante`, `avancado`,
  `ganhar_musculo`, `ambos`, `secar`, `trinca`, `elite`).
- A pagina de Protocolos hoje expõe nivel `Intermediário`, mas o
  contrato de templates aceita apenas `iniciante` e `avancado`. Nao
  inventar terceiro valor no backend; se dado real trouxer outro valor,
  tratar como exibicao defensiva e pedir decisao antes de criar
  mapeamento novo.
